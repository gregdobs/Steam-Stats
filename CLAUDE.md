# Steam Stats

Personal gaming analytics dashboard powered by the Steam Web API, HowLongToBeat, and (optionally) local Steam installation data.

## Stack

- **Frontend**: React 18 + Vite 5. All charts (donuts, bar charts, sparklines, scatter/lane plots) are hand-rolled inline SVG — no charting library. Plain CSS (`src/index.css`), no CSS framework.
- **Backend**: Express server (`server.js`) — hand-rolled HowLongToBeat scraper and VDF parser live here (no `howlongtobeat-core` or `vdf-parser` packages, those were removed as dead deps).
- **Dev run**: `npm run dev` — runs server (port 3001) + Vite frontend (port 5173) concurrently via `concurrently`. Both are reachable at `steamstats.localhost:<port>` as well as plain `localhost:<port>` — see the `.localhost` convention note below.
- **Shell**: Electron (`electron/main.js`). The main process imports `server.js` directly and points a `BrowserWindow` at it over HTTP — the Express server is *not* rewritten to use IPC, deliberately, so the app also still runs in a plain browser and stays installable as a PWA.
- **Packaging**: `npm run build:electron` → Vite build + license notice + `electron-builder` (config in `electron-builder.yml`), producing an NSIS installer and a portable single-`.exe` into `release/`.
- Node >= 22 required (`engines` in package.json).

### Packaging history — don't re-litigate these

- The pre-Electron setup (`bootstrap.cjs` + `pkg` + a bundled `node.exe`) **shipped the Node runtime twice**: a 75MB pkg executable whose only job was to spawn an 83MB `node.exe`. That was a workaround for pkg's bytecode VM refusing to run `server.js` (three documented attempts), not a design. Electron's main process is Node, so the whole problem dissolved — don't reintroduce a spawned-child-process launcher.
- A tray-icon/hidden-console launcher via `systray2` was tried and removed pre-Electron, because hiding the console left no clickable affordance and no debuggable path. Electron supersedes both halves of that: the window *is* the affordance, and DevTools (Ctrl+Shift+I, menu revealed with Alt) *is* the debug path. `autoHideMenuBar` is set rather than removing the menu, specifically to keep DevTools reachable.
- **`asar` is off on purpose** (`electron-builder.yml`). `express.static`/`res.sendFile` go through `send`, whose fs/stat/stream handling has enough asar edge cases that a packaging bug would take out the app's only window. `dist/` is ~400KB so the archive buys nothing. Verified: `/`, `/assets/*.js`, `/manifest.webmanifest` and `/icon-192.png` all serve 200 from the packaged build.
- **`electronLanguages: [en-US]`** — every UI string is English; Electron's default ~50 locale files were 47MB of translations for text that doesn't exist.
- **The build stages through `%TEMP%` on purpose — don't "simplify" it back to a plain `electron-builder` call.** `tools/build-app.mjs` runs electron-builder with its output under the OS temp dir, then copies the artifacts into `release/`. Without that, packaging fails with `EPERM … rename 'release/win-unpacked.tmp' -> 'release/win-unpacked'` whenever the project sits in an indexed/synced location (Desktop, Documents, OneDrive). Diagnosed, not guessed: the extracted `electron.exe` opens exclusively with no sharing (nothing inside is locked), the folder's ACLs grant Full Control, a fresh empty folder and a folder of 50 files both rename fine in the same parent, and the identical build succeeds under `%TEMP%`. That signature is a directory-change-notification handle — what Search Indexer/Defender/sync clients take on newly created folders — which blocks renaming the directory while leaving its contents fully accessible. Copying files is unaffected, hence the stage-then-copy shape.

## Project layout

- `src/pages/` — top-level routed views: Dashboard, Calendar, Library, Progress (backlog burn-down + completion status, merged into one page/nav item despite the filename split implied by older docs), Achievements, History. Calendar sits next to Dashboard in `NAV_ITEMS` rather than next to History on purpose — its primary layer is recent day-by-day playtime, and the adjacency is what stops "Calendar" and "History" reading as synonyms in the navbar.
- `src/components/` — shared UI pieces (Navbar, SettingsModal, SetupScreen, chart widgets, etc.).
- `src/hooks/useAppContext.jsx` — central app state/context (Steam data, caches like `achCache`).
- `src/utils/steam.js` — core stats/algorithm logic (streaks, percentiles, recommender) — not just API glue, treat as business logic. Covered by `src/utils/steam.test.js`.
- `server.js` — Express API server: Steam Web API proxy, local Steam install detection, HLTB scraping, VDF parsing.
- `electron/main.js` — Electron main process: starts the server, owns the window, single-instance lock, external-link handling.
- `tools/` — build-time generators (`generate-icons.mjs`, `generate-licenses.mjs`), both dependency-free by design.

## Documentation maintenance

Docs drifted badly once already — pages got merged/renamed, features got removed, a dependency became dead weight, and README/CLAUDE.md kept describing the old state for weeks until a dedicated cleanup pass caught it (see CHANGELOG `[Unreleased]`, doc-polish entry). Treat doc updates as part of the change itself, done in the same commit, not a follow-up task.

**When a change falls into one of these, update the doc(s) listed — right then, not later:**

| Change | Update |
|---|---|
| Add/remove/rename/merge a page or route (`src/pages/`, `App.jsx`'s `PageContent` switch, Navbar's `NAV_ITEMS`) | README `## Features` (that page's section); CLAUDE.md `## Project layout` |
| Add/remove a user-facing feature, panel, or chart within a page | README's bullet list for that page |
| Change what data a feature is derived from (e.g. local snapshots → live API, or vice versa) — especially anything affecting "needs N days of history" gating | README's description of that feature; CLAUDE.md's data-gating note in `## Conventions / notes` |
| Add an npm dependency | Actually import it somewhere before merging — a listed-but-unused dep is exactly what caused the `chart.js`/`react-chartjs-2` cleanup |
| Remove an npm dependency | `grep -rl "<pkg>"` across `src/` and `server.js` first to confirm it's dead, then also check `tools/generate-licenses.mjs`'s `SERVER_RUNTIME_DEPS`/`FRONTEND_BUNDLED_DEPS` lists and the `## Stack` line in this file |
| Add a dependency the **server** needs at runtime | Put it in `dependencies` *and* add it to `SERVER_RUNTIME_DEPS` in `tools/generate-licenses.mjs`. Anything only the frontend or the dev scripts need belongs in `devDependencies` — electron-builder ships `dependencies` verbatim, so a misplaced entry silently bloats the installer |
| Add/remove/rename a Settings modal section or tab | README `## Settings` |
| Any user-visible change worth telling someone updating the app about | CHANGELOG `[Unreleased]` — add the entry now, not retroactively at release time |

**Before calling a feature/change done:** `grep -n "<old name/behavior>" README.md CLAUDE.md` for whatever you just renamed, removed, or changed the behavior of (component name, page label, emoji badge list, data-source description, dependency name). A stale doc claim never shows up in a code diff review — the grep is the only thing that catches it.

## Conventions / notes

- Brand name is **"Steam Stats"** (with a space) in user-facing text — `SteamStats` (no space) as a literal string should not appear; watch for it creeping back into new UI copy.
- Data-driven features (Play Streak, Personal Percentile, "What Should I Play Tonight") rely on daily snapshot history accumulated over real usage — they intentionally return `null`/render nothing below minimum sample sizes (e.g. 7 days for daily percentile, 21 for weekly) rather than showing misleading numbers from small samples. Keep that "silent until meaningful" behavior when touching this code. The History page is the exception: it's built from Steam's own achievement-unlock timestamps rather than local snapshots, so it has real data from day one with no minimum-sample gating. The Calendar page straddles both — its playtime layer is snapshot-derived and gated, its achievement layer is not, which is deliberately what keeps the page from being empty on a fresh install.
- **Snapshot history is the only data in this app that cannot be re-fetched — treat it accordingly.** Steam reports lifetime totals rather than sessions, so a day nobody recorded is permanently gone; every other cache here just re-downloads. Three pieces keep it safe and they only work together: (1) `snapshots.json` in the data folder is the durable archive and holds **everything**, while `localStorage` holds a `SNAPSHOT_RETENTION_DAYS` (90) working set — it's quota-bound and shares ~5MB with the achievement/HLTB caches; (2) `POST /api/snapshots/:steamId` **merges** into the archive and must never go back to replacing it — the client only ever posts its 90-day window, so an overwrite silently truncates the durable copy to whatever the client happened to be holding (this was a real bug: the mirror was write-only, `GET` existed but nothing called it, and a cleared browser profile lost everything while a perfect copy sat unread on disk); (3) `hydrateSnapshotsFromServer()` in `steam.js` runs in `loadData` **before** `saveSnapshot`, so a fresh profile restores instead of starting a new history. The archive is delta-encoded (v2 — one base snapshot plus per-day changed games; measured 98.2% smaller, since 99.7% of a snapshot's rows repeat the previous day). `GET` reconstitutes full snapshots, so the encoding never reaches the app's data model — keep it that way. v1 files auto-migrate on read. Round-trip and merge semantics are covered in `src/utils/steam.test.js`. **`/api/snapshots` needs its own `express.json({ limit })` mount** — the global `express.json()` default is 100kb, and a real post (the client's whole 90-day window) is 1.5MB for a 311-game library and ~10MB for a 2,000-game one. That default silently 413'd everything past about five snapshots, and `saveSnapshot` fire-and-forgot the POST, so the archive just stopped receiving writes a few days into use with nothing logged anywhere. The mirror write now logs a warning on a non-OK response instead of swallowing it — don't put the bare `.catch(() => {})` back.
- **The Calendar's coverage model is the one place a missing day must NOT be treated as zero.** Every other snapshot-derived helper does `byDate.get(key) || 0` (see `getDailyPlaytimeSeries`), which is fine on a sparkline and a lie on a calendar — a blank week reads as "I didn't play" when it means "I didn't open the app". `computeDailyCoverage` in `src/utils/steam.js` therefore tri-states every day: `played`, `idle` (a clean one-day snapshot pair that genuinely showed zero) and `uncovered` (no clean pair), plus `untracked`/`future` at the edges via `resolveDayState`. Two rules to preserve if you touch it: (1) a delta is only pinned to a single date when consecutive snapshots are exactly **one calendar day** apart — wider gaps carry a real total that can't be split, so those days stay `uncovered` and expose `spanMinutes`/`spanFrom`/`spanTo` for context rather than having a daily figure invented for them (this is also what stops "days the app was reopened" rendering as playtime spikes); (2) don't collapse `idle` and `uncovered` back into one empty state — telling those two apart *is* the feature. `Calendar.jsx`'s legend is driven by the states actually present in the month on screen, so a new state needs adding there too or it'll render unexplained. Month-jumping lives in a dropdown hanging off the month title (`MonthPicker`), fill-graded by achievement-unlock volume — that's the one signal reaching back through months playtime tracking never covered. **The notice above the grid is a slot, not a fixture: `buildNotice()` returns `null` whenever the page can speak for itself, and that absent state is the correct one.** A permanent explainer becomes furniture the eye skips, which is exactly what makes it useless on the day it matters — so new conditions go into that function in priority order rather than as additional banners, and `src/pages/Calendar.test.js` asserts it stays silent on healthy data. **The rules live in `coverageFromDayRecords`, and that is the only place they may live.** It consumes DAY RECORDS — `{ from, to, minutes, games }` — produced by two sources: `buildDayRecordsFromSnapshots` (localStorage's 90-day working set) and `GET /api/snapshots/:id/daily` (the full archive, however many years deep). The server deliberately emits raw `from`/`to` timestamps and does no day-boundary maths: those rules are timezone-sensitive and are the design intent, so putting a second copy on the server would be exactly the drift this file warns about elsewhere. `firstTracked` must come from the **archive**, not localStorage — sourcing it locally makes every month older than the 90-day window claim "before tracking started" once real history accumulates, silently turning the honesty guarantee into a lie. Covered by `src/utils/steam.test.js`, including a parity test asserting both paths produce byte-identical coverage.
- When changing React state and needing the *updated* value synchronously within the same call (not just on next render), watch out for closure staleness — `useAppContext.jsx` had a real bug here (see git history on that file) and uses a ref alongside `setAchCache` to sidestep it.
- Local Steam data can no longer supply per-game launch counts — modern `localconfig.vdf` doesn't write a `LaunchCount` field (verified against a real install; see git history on `SessionInsights` removal). `server.js` still parses the field defensively (falls back to `null`), and a few UI spots (`GameDetailPanel`, Dashboard's session-count line, Settings debug info) still read `game.launchCount` and silently render nothing — don't be surprised if it's always empty.
- `vitest` is wired into `package.json` (`npm test`); `src/utils/steam.test.js` covers algorithm functions in `steam.js` (streaks, percentiles, snapshot-derived series, unlock aggregation). Extend that file rather than reaching for ad hoc scripts when touching this logic.
- **`steamstats.localhost` is the app's real, intended address, not a placeholder or typo.** `*.localhost` is reserved by RFC 6761 and every modern browser resolves it to loopback with zero setup — no hosts file, no admin rights. Electron's `BrowserWindow` loads it, `server.js`'s startup log prints it, and the README leads with it. (Verified: Electron's Chromium resolves it exactly like a normal browser.) Plain `localhost` is kept deliberately in exactly one place — `electron/main.js`'s internal `waitForServer` health poll — because that's a Node-to-Node call, not a browser navigation, and the `.localhost`-resolves-to-loopback behavior is a browser convention Node's own resolver isn't guaranteed to share. If you add a new place that opens or prints a URL for the *user* to see/click, use `steamstats.localhost`; if you add internal (non-browser) request code, use plain `localhost`. If you ever change the dev or server port, update it in all four places at once: `electron/main.js` (`PORT`, which feeds the health-check and window URLs), `server.js` (startup log + the `cors()` origin allowlist, which hardcodes both the plain and `steamstats.localhost` variants of each port), and the README. **Be aware that changing the port also orphans every bit of `localStorage`** — it's keyed by origin *including* the port, so `steamstats.localhost:3001` and `steamstats.localhost:3002` are different stores. That's snapshot history, theme, config and the achievement/HLTB caches, all appearing to vanish at once. The snapshot archive survives it (see the snapshot durability note below) and rehydrates on next launch; nothing else does. The same split is why the packaged app (`:3001`) and `npm run dev` (`:5173`) keep genuinely separate localStorage — they're different origins, so testing in one tells you nothing about the other's stored state.
- **The native window frame follows the app theme, via the one IPC channel this app has.** Windows draws the title bar from Chromium's dark-mode state, so without this a white caption bar sits on top of a near-black app. `electron/main.js` sets `nativeTheme.themeSource = 'dark'` *before any window exists* — doing it later gives a visible light-to-dark flip on launch — and `electron/preload.cjs` exposes exactly one function (`window.steamStatsShell.setFrameTheme`) that the theme effect in `useAppContext.jsx` calls, so picking the Light glass theme turns the frame light too. Three things to preserve: (1) the preload is **`.cjs`** because the project is `"type": "module"` and preload scripts load as CommonJS — naming it `.js` makes Electron parse it as ESM and fail silently, leaving the frame stuck on the startup default; (2) the renderer call is optional-chained, because `window.steamStatsShell` is undefined in a browser or PWA where there's no frame to match — that's also why this stays a cosmetic-only channel and the Express server remains how the app talks to its backend (see the packaging notes); (3) the default is `'dark'` rather than `'system'` on purpose — three of the four themes are dark and the app opens on the dark one, so `'system'` would flash the wrong frame for most users on a light Windows. Verified by sampling the caption's pixels (RGB ~30,32,35 after, white before) and by confirming the IPC actually arrives — worth doing together, since the startup default alone produces a dark frame even if the preload never loads.
- **The service worker (`public/sw.js`) must stay non-caching.** It exists for one reason: browsers only offer "Install app" for a page that registers a fetch handler, and installing is what gives Steam Stats its own window and taskbar icon. It is *not* the start of an offline story. Adding a precache here would be actively wrong — assets come from `127.0.0.1` (no latency to save), the app can't function without its local server anyway (nothing meaningful to serve offline), and a stale cache would keep serving the old build's JS after someone unzips a new release. **It must never call `respondWith` on a cross-origin request** — that mistake shipped in 1.2.0 and broke every image in the app. `event.respondWith(fetch(event.request))` re-issues the request as a `fetch()`, and a `fetch()` is policed by `connect-src` (here `'self'`) instead of the directive matching the original request type. An `<img>` pointing at Steam's CDN is fine under `img-src`, but laundering it through the worker turned it into a forbidden connection, so all game art and the avatar failed with `Refused to connect… at sw.js`. The handler now early-returns for anything not same-origin. Note this also means **the CSP is not the place to "fix" image loading** — `img-src` was correct the whole time. It's registered from `src/main.jsx` behind `import.meta.env.PROD` **and** a `!isElectron` user-agent check — the first so it never sits in front of Vite's HMR in dev, the second because the Electron build is already an installed app and has no install prompt to earn. Keep both guards. The Electron branch also actively **unregisters** any existing worker, and `electron/main.js` clears `serviceworkers` storage on the session before the window loads. Both are needed, and the session clear is the one that actually works: skipping registration does nothing about a worker a previous version installed, and renderer-side `unregister()` doesn't release control of the current page — it applies once every client closes, so the first launch after a fix is still served by the broken worker. If you're ever debugging "my service worker change had no effect", check `navigator.serviceWorker.controller` rather than the registration count; 1.2.0's worker showed `registrations: 0` while still controlling the page. If offline support is ever actually wanted, that's a deliberate redesign with a cache-busting story, not a few lines added to this file.
- The installable-app icons in `public/` (`icon-192.png`, `icon-512.png`, and `-maskable-` variants) are generated by `npm run build:icons` (`tools/generate-icons.mjs`), which hand-encodes PNG via Node's built-in `zlib`. That's on purpose — don't add `sharp`/`jimp`/`canvas` to regenerate four flat images; edit `drawIcon()` and re-run. Note `public/favicon.svg` is a separate thing (an emoji in an SVG `<text>` element) and isn't suitable as an app icon, which is why real PNGs exist alongside it.
- **Fonts are bundled in `public/fonts/`, not loaded from Google — don't "simplify" that back to a `<link>` tag.** The CSP is `style-src 'self' 'unsafe-inline'`, so an external font stylesheet is refused outright; that's how this was broken for months without anyone noticing (packaged builds silently rendered in the system sans). Beyond that, a local-first app shouldn't phone a CDN on launch, and a desktop app served from `127.0.0.1` shouldn't need the network to draw text. DM Sans is the *variable* font so one file spans 300–700; DM Mono has no variable cut, hence separate 400/500 files. `latin` and `latin-ext` are both shipped because Steam game titles aren't ASCII-only. If the font set changes, `tools/generate-licenses.mjs` picks the families up from the filenames in that folder — keep the `dm-sans`/`dm-mono` prefixes or the OFL attribution silently drops out.
- **Artwork fallbacks must vary CDN *host*, not just image path** (`getGameCapsuleFallbacks` in `src/utils/steam.js`). Steam fronts identical assets from cloudflare/fastly/akamai. The original list was five paths on `cdn.akamai` alone, so one unreachable host made *every* game in the library render the placeholder simultaneously — a whole-library outage from a single point of failure. Host is varied before shape because a host outage affects every asset for every game, while a missing capsule size affects one title. `cdn.akamai` is the legacy endpoint and is deliberately last. `src/utils/steam.test.js` asserts the fallbacks never collapse onto one host.
- **Steam serves four unrelated families of image from four different host sets, and `imgSrc` in `server.js` has to list all of them.** Game art comes from `cdn.*.steamstatic.com` and `shared.*.steamstatic.com`, avatars from `avatars.*`, and **achievement icons from `steamcdn-a.akamaihd.net`** — an entirely separate legacy host that `GetSchemaForGame` returns absolute URLs for. That last one was missing, so every achievement icon in the app rendered blank in any build served by this server, while looking perfect in dev (Vite on `:5173` applies no CSP at all — the same shape of trap as the Google-Fonts bug in 1.2.1). Verified per host by fetching one icon path: `steamcdn-a.akamaihd.net`, `media.steampowered.com` and `cdn.cloudflare.steamstatic.com` return `image/jpeg`; the `community.*.steamstatic` edges return an HTML 404 and are deliberately not listed. **When images go blank, there are two suspects with identical symptoms** — a CSP refusal (check the console) and a stale service worker (check `navigator.serviceWorker.controller`, not the registration count). Chasing the wrong one wastes a lot of time, because a controlling worker blocks *every* cross-origin image including already-whitelisted hosts, which reads exactly like a CSP problem.
- **Steam store links route through the `steam://` protocol when a local install was detected** (`steamStoreUrl`/`shouldUseSteamApp` in `src/utils/steam.js`). Two things to preserve if you touch this: (1) the preference is *tri-state* — `undefined` means "auto, follow detection", and collapsing it to a plain boolean would make "never chose" indistinguishable from "explicitly turned it off", so connecting Steam later could no longer start routing links; (2) `steamStoreUrl` validates the appid against `/^\d+$/` and returns `null` otherwise, because that string is handed to the OS URL handler via Electron's `shell.openExternal` — don't relax it. The setup screen's API-key link stays on `https://` on purpose: it's a logged-in account page that belongs in the user's real browser, not the Steam client's built-in one.
- **"Game details → Public" is a separate Steam privacy toggle from overall profile visibility**, and it's the actual gate on `GetOwnedGames` (a private profile still returns a player object from `GetPlayerSummaries`, just an empty games list). This was a real onboarding footgun — a bad API key, a mistyped profile URL, and this toggle being off used to all surface as the same one or two generic error messages. Now: `server.js`'s `forwardSteamError` forwards Steam's real HTTP status (401/403 → bad key, network failure → unreachable) instead of a flat 500; `useAppContext.jsx` distinguishes "no profile found" (bad URL/ID) from a genuinely empty library; `Dashboard.jsx`'s `EmptyLibraryState` catches the empty-library case specifically. Keep new Steam-connection error paths this specific rather than collapsing them back into one message.
